DevSecOps
Security testing pipeline for Penpot
role Secret management & testing leadteam Four, semester projectread ~6 min

Executive summary

Penpot is an open-source design platform deployed via Docker Compose. Our team assessed it end to end and built automated security tests around the weakest areas. The headline issue was a default master key shipped in the deployment configuration, meaning any operator who deployed the stack unchanged inherited a publicly known secret capable of signing and decrypting sensitive tokens.

Scope and environment

We deployed Penpot locally with Docker Compose to give ourselves a realistic, isolated target: frontend, backend, exporter, PostgreSQL, and Redis. All testing was confined to that lab instance. The goal was not just to find bugs but to build repeatable tests that would catch the same issues on the next deployment. Work was split across four tracks: secret management, session invalidation, rate limiting, and system hardening. I owned secret management and the security testing that grew out of it.

Method

  • Composition analysis. Generated a software bill of materials with Syft to inventory dependencies and flag outdated components.
  • Configuration review. Read the Compose files and environment variables the way a first-time operator would.
  • Active testing. Proxied the application through Burp Suite to inspect authentication, cookie flags, and session behaviour.
  • Transport security. Ran testssl.sh and checked response headers against the OWASP Secure Headers project.

Findings

FindingSeverityImpact
Default master key in deployment configCriticalA publicly known secret used for signing and encryption. An attacker who knows the default can forge or decrypt tokens on any unchanged deployment.
Session cookie missing Secure flagHighSession token can travel over plaintext HTTP, exposing it to interception on an untrusted network.
No rate limiting on auth endpointsHighLogin and token endpoints accepted rapid repeated requests, enabling credential brute force.
Missing transport security headersMediumNo HSTS, so a downgrade to HTTP is not prevented on later visits.
Verbose version disclosureLowComponent versions in responses make it trivial to map the deployment to known CVEs.

The default master key

The deployment ships with a placeholder secret in its environment configuration. It is documented as something to change, but nothing enforces that, and the application starts happily without it being touched. That gap between documented and enforced is the actual vulnerability. The fix is to make the insecure state impossible rather than merely discouraged: generate the key at deploy time and fail closed if it still matches the shipped default.

# Generate a strong master key instead of shipping one
openssl rand -base64 48 > .penpot-master-key

# Fail the deployment if the default value is still in place
grep -q "default-master-key" .env && \
  echo "FAIL: default master key still present" && exit 1

Automating the checks

The point of the project was to stop these regressing. Each finding became a test that runs on every build, so a bad configuration fails the pipeline rather than reaching a deployment.

def test_secure_cookie_flag(session_response):
    """Session cookies must be Secure and HttpOnly."""
    cookie = session_response.cookies.get("auth-token")
    assert cookie.secure is True
    assert cookie.has_nonstandard_attr("HttpOnly")

def test_hsts_header_present(response):
    """Transport security must be enforced, not optional."""
    assert "Strict-Transport-Security" in response.headers

Remediation summary

  1. Generate the master key at deploy time and fail the build if the default persists.
  2. Set Secure, HttpOnly, and SameSite on all session cookies.
  3. Add rate limiting to authentication and token endpoints.
  4. Add HSTS and the remaining OWASP-recommended headers at the reverse proxy.
  5. Run SBOM generation on every build and alert on newly disclosed CVEs.

What I took from it

The most severe issue was not a clever exploit. It was a default nobody was forced to change. Secure defaults matter more than secure documentation, and the only reliable way to enforce them is to make the pipeline refuse to ship without them.
Network Security
Enterprise network security lab
course SPR708team Group of threemethod Purple team, PEIRread ~7 min

Executive summary

A full defensible enterprise built from scratch across six virtual machines, then tested with a purple team exercise. The design layers segmentation, a web application firewall, an intrusion detection system, and centralized logging so that a single control failing does not expose the whole environment. Every attack technique was validated against its intended defensive control.

Architecture

The topology used six segmented virtual machines rather than a flat network, so traffic between tiers had to pass through a controlled boundary:

  • Perimeter router on Ubuntu with nftables enforcing segmentation between the user, server, and DMZ zones.
  • Reverse proxy and WAF using ModSecurity with the OWASP Core Rule Set in front of the web application.
  • Custom PKI issuing internal certificates so services could enforce TLS with a trusted internal root.
  • Suricata IDS monitoring the span of inter-zone traffic.
  • Wazuh SIEM collecting endpoint and network telemetry into one place.
  • Active Directory with Group Policy Objects, TOTP multi-factor authentication, and OpenVPN for remote access.
  • Containerized services for the application tier, kept off the host directly.

Defensive controls

The design goal was defense in depth. A short list of what each layer was responsible for:

ControlDefends against
nftables segmentationLateral movement between zones
ModSecurity WAFWeb application attacks (injection, traversal)
Suricata IDSKnown exploit signatures and scanning
GPO hardening + MFACredential misuse and weak configuration
Wazuh SIEMBlind spots, by centralizing detection

Purple team validation

Rather than only building, we ran a purple team simulation using the PEIR methodology, which pairs each offensive action with the detection it should trigger. Findings were mapped against both MITRE ATT&CK (what the attacker did) and MITRE D3FEND (what the defense should do). This turned the exercise from opinion into evidence: for each technique we could say whether the control fired, and if not, why.

# Example inter-zone policy: default deny, explicit allow
table inet filter {
  chain forward {
    type filter hook forward priority 0; policy drop;
    iifname "user0" oifname "dmz0" tcp dport { 443 } accept
    ct state established,related accept
    log prefix "DROP_FWD " drop
  }
}

Outcome

The exercise confirmed most controls behaved as designed and exposed a handful of visibility gaps where an action succeeded without a matching alert. Each gap became a tuning task: a new Suricata rule, a Wazuh decoder, or a tighter GPO. The value was the closed loop of attack, detect, and improve.

What I took from it

Building controls is the easy half. Proving they work under a realistic attack is where the learning is, and mapping to ATT&CK and D3FEND kept that assessment honest rather than assumed.
App Pentest
Web & API penetration test
targets OWASP Juice Shop, crAPIformat First-person pentest reportread ~6 min

Executive summary

Hands-on testing of two deliberately vulnerable applications covering the modern web and API attack surface. The work moved from authorization flaws through token manipulation to server-side code execution, with each finding documented in the shape of a real engagement report: reproduction, impact, and remediation.

Approach

All traffic was proxied through Burp Suite so I could inspect and replay every request. I worked the OWASP Top 10 and the OWASP API Security Top 10 methodically rather than chasing single flags, since the goal was coverage and clear reporting, not just capture.

Findings

FindingSeverityNote
Broken object level authorization (BOLA)CriticalChanging an object ID in an API request returned another user's data.
OS command injectionCriticalUnsanitized input reached a shell call, allowing arbitrary command execution.
JWT manipulationHighWeak signature handling allowed forging a token with elevated privileges.
Mass assignmentHighAdding an unexpected field to a request body changed a role the client should not control.
GraphQL introspection and IDORMediumIntrospection exposed the full schema, and object references could be walked.
Server-side template injection (SSTI)HighTemplate input was evaluated, a path to code execution.
Cross-site request forgery (CSRF)MediumState-changing requests lacked anti-CSRF protection.

BOLA, the recurring theme

The most impactful class was authorization. Applications frequently authenticate a user correctly and then trust the object ID the client supplies. Walking those IDs returned data belonging to others, which is exactly the pattern behind many real-world API breaches.

# Authenticated as user A, requesting user B's resource
GET /api/v2/user/orders/1024 HTTP/1.1
Authorization: Bearer <user-A-token>

# Server returns user B's order instead of 403 Forbidden
# Fix: enforce ownership server-side, never trust the client ID

Remediation themes

  • Enforce authorization on the object, server-side, on every request.
  • Verify JWT signatures strictly and reject unexpected algorithms.
  • Allowlist assignable fields instead of binding the whole request body.
  • Disable GraphQL introspection in production and paginate object access.
  • Never pass user input to a shell or template engine without strict validation.

What I took from it

Authentication and authorization are not the same control, and most of the serious findings lived in the gap between them. Writing each one up as a reproducible report was as much of the skill as finding it.
Detection Lab
MS17-010 (EternalBlue) detection
technique T1210 Exploitation of Remote Servicesfocus Network detection engineeringread ~5 min

Executive summary

A detection engineering project for MS17-010, the SMBv1 flaw behind EternalBlue. Rather than run live exploit tooling, I generated synthetic traffic carrying the protocol markers of the exploit, wrote Suricata rules to catch it, and validated the alerts through Wazuh. The result is a repeatable detection proven against known-bad input.

Why synthetic traffic

Running EternalBlue against a real host is noisy, fragile, and unnecessary when the goal is detection. What a detection engineer needs is traffic that reliably contains the fields a signature keys on. Generating that with Scapy makes the test deterministic and safe to run anywhere.

from scapy.all import IP, TCP, Raw, wrpcap

# SMB transaction fragment associated with the MS17-010 exploit path
pkt = IP(src="10.0.0.5", dst="10.0.0.10") / \
      TCP(sport=49555, dport=445, flags="PA") / \
      Raw(load=b"\xff\x53\x4d\x42\x25...")   # SMB header + trans marker

wrpcap("ms17-010-sample.pcap", [pkt])

The Suricata rule

The rule targets SMB traffic to port 445 and the transaction pattern the exploit relies on, with a reference back to the CVE so an analyst gets context in the alert.

alert tcp any any -> $HOME_NET 445 ( \
  msg:"MS17-010 EternalBlue SMBv1 transaction pattern"; \
  flow:to_server,established; \
  content:"|ff|SMB"; offset:4; depth:4; \
  reference:cve,2017-0144; \
  classtype:attempted-admin; sid:1000010; rev:1; )

Validation

Replaying the PCAP through Suricata in offline mode confirms the signature fires exactly once per attempt, with no alerts on benign SMB captured separately. That negative test matters as much as the positive one: a rule that also fires on normal file sharing is useless.

Test inputExpectedResult
Synthetic MS17-010 PCAPAlertFired
Benign SMB file transferNo alertClean

Wazuh integration

Suricata alerts are forwarded into Wazuh so the detection lives alongside the rest of the telemetry. A custom decoder and rule raise the alert level and tag it with the ATT&CK technique, so it surfaces on the dashboard the way a real SOC would triage it.

What I took from it

A detection is only trustworthy if you can show both that it catches the attack and that it stays quiet on normal traffic. Building the test data by hand forced me to understand the protocol behaviour, not just copy a rule.
Threat Hunting
Splunk threat hunt (BOTSv3)
dataset Boss of the SOC v3sources CloudTrail · Cisco ASA · DNSread ~5 min

Executive summary

A structured hunt through Splunk's Boss of the SOC v3 dataset, reconstructing an attack chain that spanned cloud API abuse, network traffic, and DNS. The work started with a data problem: the dataset had been ingested incorrectly, and fixing the ingestion was the first real lesson before any hunting could begin.

Fixing the data first

Early queries returned nothing useful because the source types had not been assigned correctly on ingest, so timestamps and fields were not parsing. Re-ingesting with the right source typing was a reminder that a hunt is only as good as the data model underneath it. Bad parsing looks exactly like no evidence.

Cloud: CloudTrail

With clean data, I pivoted through AWS CloudTrail to find suspicious API activity: unusual identities, access key usage, and configuration changes that did not fit normal patterns.

index=botsv3 sourcetype=aws:cloudtrail
| stats count values(eventName) by userIdentity.userName, sourceIPAddress
| sort - count

Network: Cisco ASA

Firewall logs tied the cloud activity to network behaviour, letting me confirm which hosts were involved and when connections were made.

DNS exfiltration

The most interesting thread was DNS. Data exfiltration over DNS hides payloads inside query names, which shows up as abnormally long or high-volume lookups to a single domain. Aggregating query length and count per domain surfaced the channel.

index=botsv3 sourcetype=stream:dns
| eval qlen=len(query)
| stats count avg(qlen) as avg_len by query
| where avg_len > 40 AND count > 100
| sort - count

What I took from it

Two things stuck. First, verify your data before you trust a negative result. Second, an attack rarely lives in one log source, so the hunt is really about pivoting across cloud, network, and DNS until the story is consistent.
Threat Hunting
Active Directory recon detection
lab Capsulecorpactivity AdFind reconnaissanceread ~5 min

Executive summary

Attackers who land in an Active Directory environment almost always map it before moving. This project simulated that reconnaissance with AdFind, mapped each action to a MITRE ATT&CK discovery technique, and built Wazuh detection rules so the same behaviour would raise an alert next time.

The behaviour to catch

AdFind is a legitimate administration tool, which is exactly why attackers reuse it. It queries the directory for users, groups, computers, and trust relationships. In the Capsulecorp lab I ran realistic discovery commands and observed what they left behind in the logs.

Recon actionATT&CK technique
Enumerate all domain usersT1087 Account Discovery
Enumerate privileged groupsT1069 Permission Groups Discovery
Enumerate domain computersT1018 Remote System Discovery
Query domain trustsT1482 Domain Trust Discovery

Building the detection

Rather than alert on the tool name alone, which is easy to evade by renaming the binary, I keyed detections on the pattern of LDAP queries and process behaviour captured by Sysmon and forwarded to Wazuh. A custom rule raised the alert level when the tell-tale combination of discovery queries appeared from a single host in a short window.

<rule id="100210" level="10">
  <if_sid>92000</if_sid>
  <field name="win.eventdata.image">\\adfind\.exe$</field>
  <description>AD reconnaissance: AdFind execution (T1087/T1069)</description>
  <mitre><id>T1087</id><id>T1069</id></mitre>
</rule>

The renaming problem is why the stronger rule looks at behaviour, not just the filename: a burst of user, group, and computer LDAP queries from one workstation is suspicious regardless of what the binary is called.

What I took from it

Detecting misuse of legitimate tools is harder and more valuable than detecting malware. The reliable signal was the pattern of activity mapped to ATT&CK, not any single indicator that an attacker could trivially change.
Recon
API reconnaissance on bug bounty targets
scope Authorized public bug bounty programsfocus Attack surface mappingread ~5 min

Executive summary

Reconnaissance against in-scope public bug bounty targets, staying strictly within program rules. Good recon turns a vague target into a concrete, prioritized attack surface before a single active test runs. This writeup covers the methodology rather than any single vulnerability.

Rules of engagement

Everything here was performed only against assets explicitly listed as in scope, at reasonable request rates, with no exploitation beyond what was needed to confirm a finding. Reconnaissance discipline starts with reading the program policy, not with running tools.

Surface mapping

The first pass builds a map: what hostnames exist, what is reachable, and what technology sits behind each one. Passive sources come first because they are quiet and cheap.

# Passive subdomain discovery
amass enum -passive -d target.example -o subs.txt

# Resolve and probe for live hosts and technology
cat subs.txt | httpx -silent -status-code -tech-detect

Content and endpoint discovery

With live hosts identified, directory and parameter fuzzing surfaces API paths that are not linked anywhere. A curated wordlist matters more than raw thread count.

ffuf -u https://api.target.example/FUZZ \
     -w api-wordlist.txt -mc 200,401,403 -o ffuf.json

Findings pattern

ClassSeverityNote
Publicly readable storage bucketHighEnumerated with S3Scanner; world-readable, though contents were non-sensitive.
Internal header disclosureMediumBackend framework and internal hostnames leaked in response headers.
Verbose error responsesLowStack traces on malformed input aided fingerprinting.

Reporting

Each finding was written up with clear reproduction steps, an impact statement in business terms, and a remediation suggestion. A finding a triager can reproduce in two minutes is worth more than a clever one they cannot follow.

What I took from it

Most of the value was in the boring part: careful scoping, quiet passive collection, and organized notes. Recon rewards patience and record-keeping far more than aggression.
